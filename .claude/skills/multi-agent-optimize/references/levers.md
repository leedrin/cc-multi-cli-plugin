# 优化杠杆目录（症状 → 杠杆 → 做法 → 证据）

来自 openspec-multi-apply 从 v1 到 v6 的优化经验。每个杠杆写了：看到什么信号时用、具体怎么改、我们改完的实测效果、副作用。报告里的诊断信号用这里的编号。

通用原则，先读这三条：

1. **子 agent 的钱花在「读」上**。输出几乎可以忽略（网关甚至记 0），单次成本 ≈ 回合数 × 每回合上下文。所以少一次派单、少读一个大文件、少一个回合，比让回答更短更值钱。
2. **主 agent 的钱跟派单次数走**。每次派单主 agent 要写派单、等通知、读回执、决定下一步，约 2.2–2.7 次调用；上下文越长，每次调用越贵，还会触发压缩。减少派单同时省两边。
3. **流程规则比个人能力重要**。子 agent 多跑几轮几乎都是因为「该一次做完的事被拆开了」或「不知道什么时候算完」，改规则比换模型便宜。

---

## L1 修复收敛

- **信号**：修复轮占子 agent 等效输入 >30%；≥20% 的单元修到 d 轮以后；同一条发现反复出现。
- **做法**：
  - 审查发现分类型（缺陷 / 测试），修复者按类型处理，测试类问题不再引出新一轮代码审查。
  - 写明「什么时候算修完」：点名条目全部有结论即可，不追加新范围。
  - 设循环上限（我们用 4），超过就停下来问用户，不要无限修。
- **证据**：v4→v6 修复轮占比始终最大（37%→61%）。离群单元 T025c2 修到 h 轮（用户特批 3 轮），一张单就占了那期近 12% 的子 agent 输入——上限本身是必要的，特批要慎用。
- **副作用**：上限太低会增加中断求助（L10）；v4.1 把上限从 3 调到 4 正是为了少打断用户。

### L1 的两个配套做法（v7 起试行）

- **风险单先出设计要点**：修复轮多的单并不是工作量大的单（首轮执行成本和修复次数的相关系数只有 −0.14），而是并发状态机、外部契约、算法取舍、内容质量这几类单。命中信号时先派一次设计探路，写清不变量、真实契约和选定方案。
- **升级制**：进入第 2 个修复轮就改派更强的执行者，先写根因再统一改。按「进入第 2 修复轮」这个已经观察到的信号触发，比事先预测难度可靠。
- **怎么判断升级有没有用**：对比 `escalation.*`，升级前的版本就是对照组。升级后的单元 ≥4 个才下结论。满足下面两条就保留：
  - `fix_after_avg` 比对照组低 30% 以上，或 `closed_in_one` ≥0.3；
  - `cost_after_avg` × 单价比 < 对照组。
  两条都不满足就取消升级，只保留设计探路。
- **证据**：v6 对照组（全 luna）有 8 个单元进入第 2 修复轮，其后平均再修 4.25 轮，没有一个一轮收敛，其后平均再花 11.2M。

## L2 复审触发

- **信号**：每单元审查 >2 次；复审单次输入接近首审。
- **做法**：复审只在「改了审查点名以外的文件（测试文件不计）」时触发；复审只核对上一轮点名的条目（派单里给「核对条目」路径），不重新全审。
- **v7 做法**：复审限定只读四样东西（必须保持、条目段落、发现核实、点名位置和本轮改动），新发现只报本轮改动行，审查范围不再给整单 diff。
- **证据**：v5 引入 1A 后复审次数/单元 1.5→1.6 基本持平；但 v6 复审单次输入 408K，几乎等于首审的 427K，说明复审仍在全量重读——「只核对点名条目」还没真正落地，这是下一个可做的点。

## L3 边做边落盘

- **信号**：出现「补录 / 补回执 / 补先红证据」类派单；验收因为证据缺失判不通过。
- **做法**：执行者拿到关键证据（修复前的失败输出、命令结果）就立刻追加进回执文件，不等到最后写总结；验收员对缺失证据记「存疑」而不是判失败，避免为了补一段日志再派一次执行者。
- **证据**：v4 期补录 6 次，单次输入 762K（接近一次验收的 879K）；v5 引入 2A 后，v6 期补录降到每单元 0.05 次。

## L4 验收少读

- **信号**：单次验收输入 > 首轮执行的 50%；验收单次输入随工单变大线性增长。
- **做法**：验收员只读回执里的「文件清单」和「发现核实」部分；用 `git status --short` + `git diff --stat` 确认范围，只对点名文件看 diff；验收命令照工单跑，不重新审查代码。
- **证据**：早期分析里验收占子 agent 成本 17%，单次 499K，首轮执行才 285K——验收比干活还贵。v3→v4 每单元验收 2.93→1.14 次（-61%）。
- **副作用**：验收变浅以后，质量要靠审查兜底；不要同时削减审查。

## L5 合并派单

- **信号**：每单元派单 >8；主 agent 每次派单 >2.2 次调用；有很多「顺手做一下」的小派单（挪文件、改一行状态）。
- **做法**：把同一个角色前后相邻的动作合进一次派单（验收员验收通过后直接提交和收尾）；修复单不再单独起文书派单；多个文书动作攒成一张清单一次做完。
- **证据**：v3→v4 每单元派单 11.47→8.43（-26%），每单元主调用 26.25→18.19（-31%），主 agent 等效输入 -32%。
- **注意**：派单数下降不会让主调用等比例下降，每次派单的往返（≈2.5 次调用）几乎不变；要继续压主 agent 得靠 L6/L8。

## L6 短回答

- **信号**：子 agent 平均回传 >1500 字符。
- **做法**：最终回答限定行数（我们用 ≤15 行），完整报告写到约定文件，主 agent 需要时自己读指定段落。
- **证据**：v3 到 v6 回传均值一直在 2.4–2.5K 字符，没降下来，说明 ≤15 行的规则没管住。先按类别看 `cat.<类别>.returned_avg` 找出回传最长的角色，再在它的输出格式里写死「只回文件路径 + 条目数 + 结论」。

## L7 只给路径

- **信号**：派单提示平均 >1500 字符；派单里贴了工单全文、上一轮报告全文。
- **做法**：派单只给路径和编号（工单路径、回执路径、核对条目路径），子 agent 自己去读；固定规则放到 agent 配置文件，不在每次派单里重复。
- **证据**：v3 把角色规则迁到 `.claude/agents/`、`.codex/agents/` 后派单提示稳定在 ~850 字符。

## L8 上下文管理

- **信号**：每 100 次派单压缩 >3 次；出现手动 `/compact`；压缩后主 agent 重读大量文件。
- **做法**：主 agent 不读子 agent 的全文产物；续跑状态写进文件（计划、工单目录），压缩后读状态文件而不是回忆；SKILL.md 保持短，把格式模板拆到 references/ 按需读。
- **证据**：压缩次数跟主上下文大小相关，跟派单次数关系不大；v4.1 把数据格式拆到 references 后压缩/100 派单从 4.17 降到 2.90（样本小，看方向）。

## L9 文书降级

- **信号**：每单元文书 >1 次；文书派单用的是和执行者一样贵的模型。
- **做法**：机械性工作（挪工单、建目录、照清单写文档）交给便宜模型的专职文书员（Claude 用 Haiku，Codex 用 luna low），主 agent 给出逐条清单，文书员照抄不发挥。
- **证据**：v6 文书单次未缓存输入 124K→43K（-66%），并且不再占用 OpenAI 额度。
- **注意**：换模型或 effort 之前先问用户。文书次数本身没降（1.2→1.65/单元），下一步是把文书动作并进验收员收尾（L5）。

## L10 中断与确认

- **信号**：用户中断 >0；主 agent 频繁停下来问「是否继续」。
- **做法**：把「什么时候必须问用户」写成封闭清单（装软件、换模型、删数据、强推、对外发消息），清单以外默认继续；循环上限到了才问。
- **证据**：v4 以后中断基本为 0；中断本身不贵，贵的是中断后主 agent 重建上下文。

---

## 样本可比性（不是杠杆，是读结论前的检查）

- 首轮执行单次成本变化 >30%：工单难度变了，绝对值对比要打折，看比例指标。
- 纯新单元 <5：只看方向。
- 离群单元（修到 e 轮以后、或单元输入 > 中位数 3 倍）：单独列出来，算一遍去掉它们后的结果再下结论。
- 新旧两版混跑同一张单：这张单不算纯新单元，已经被脚本排除在分母外。
