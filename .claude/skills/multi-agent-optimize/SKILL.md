# 多 agent 技能持续优化

编排型技能（一个主 agent 派多个子 agent）的成本和质量问题藏在几百次派单里，凭感觉改很容易「这里省了那里多了」。本技能把我们优化 openspec-multi-apply 的做法固化成一个闭环：**测 → 诊 → 改 → 验 → 记**。每一轮都有数据、有预期、有结论、有台账，下一轮从上一轮的结论出发。

所有数据和报告放在仓库 `_skill-metrics/<技能名>/`，脚本在本技能 `scripts/`，只用 Python 标准库。

```
_skill-metrics/<技能名>/
  profile.json    技能画像：派单怎么分类、「单元」是什么、角色映射（手写，见 references/profile.md）
  versions.json   版本台账：每版生效时间、指纹、措施、量化预期（version.py 维护）
  snapshots/<v>/  每版被跟踪文件的快照
  data/           每个会话一份采集结果（collect.py 生成，已脱敏，可进 git）
  reports/        对比报告 .md / .html / .json
  journal.md      优化日志：假设、结论、下一步（人写，每轮追加）
```

## 方法论：一轮优化的五步

### 1. 测：建立基线

先采集，再说话。基线要满足两个条件，否则后面的对比没有意义：

- **口径固定**：用「每单元」（如每张工单）归一，不要比总量——两段时间做的工单数不同。单元、类别、角色怎么定义写在 profile.json，一旦定下不要随手改；要改就重跑所有期的分析。
- **样本够用**：一期至少 5 个「纯新单元」（在本期开始且在本期验收的单元）。跨期的老单元会把上一版的成本带进来。

```bash
S=.claude/skills/multi-agent-optimize/scripts
python $S/collect.py --skill <技能名>                # 增量采集，未变化的会话自动跳过
python $S/version.py scan --skill <技能名>           # 会话里出现过哪些技能指纹，归到了哪版
python $S/analyze.py --skill <技能名> --b <版本或区间>  # 单期画像
```

### 2. 诊：找钱花在哪

看报告的三张表，按这个顺序：

1. **子 agent 按类别**：等效输入占比最高的前两类就是主战场。单次输入高 → 读得太多（L4、L7）；次数多 → 流程多了环节（L1、L2、L5）。
2. **每单元派单结构**：修复轮、复审、验收的次数/单元，和最深轮次分布。修到 d 轮以后的单元是离群点，去「热点派单」里看它们的标签，常常是一两张难单拖高了平均。
3. **主 agent**：每次派单的主调用、回传字符、压缩次数。主 agent 的开销跟「派单次数 × 每次派单的往返」走，不跟子 agent 的活儿走。

报告里的「诊断信号」按 references/levers.md 的杠杆编号给出，是提示不是结论——每条都要回到热点派单和会话原文核实一两个例子再动手。

### 3. 改：先登记预期，再改技能

一轮只动一两个杠杆，否则事后分不清谁起了作用。改之前写下**可验证的预期**：指标、方向、目标值。改完、开跑之前登记版本（会快照当前文件）：

```bash
python $S/version.py register --skill <技能名> --id v7 --title "一句话" \
  --measure "做了什么（一条一件事）" \
  --expect "per_unit.fix <= 1.8 | 修复轮回到 1.8 以下" \
  --expect "cat.验收.avg_cost <= 300000 | 单次验收等效输入 ≤300K"
python $S/version.py check --skill <技能名>   # 技能文件改了但没登记会报错
```

Claude 和 Codex 两版技能要同一轮一起改、一起登记，不然两边数据不可比。改的时候遵守仓库对技能的约束（例如换模型或 effort 先问用户）。

### 4. 验：跑真实工作，再对比

用新版跑够样本（≥5 个纯新单元）再分析，别跑两三张就下结论。

```bash
python $S/collect.py --skill <技能名>
python $S/analyze.py --skill <技能名> --a v6 --b v7
# 也可以用区间：--a v4..v5（版本区间，两端都含）、--a v4,v5、--a 2026-09-20..2026-09-28T15:23:04Z
```

读结论时注意报告里的「样本可比性」信号：

- **首轮执行变贵很多**（±30%）多半是这期工单更难，不是技能变差。这时看比例类指标（每派单主调用、验收/首轮执行比、修复轮占比），少看绝对值。
- **单元太少**（<5）的期只看方向，不看幅度。
- 预期「部分达到」说明方向对、力度不够；「未达到」且方向反了，先查是不是混杂因素，再考虑回退。

### 5. 记：写进台账和日志

在 `_skill-metrics/<技能名>/journal.md` 末尾追加一段（模板见 references/journal-template.md）：假设、措施、预期 vs 结果、归因、下一步。结论要带报告文件名，方便以后回溯。下一轮从「下一步」开始。

## 报告怎么读、怎么交付

- `reports/<名字>.html` 离线可开，含关键指标卡、预期核对、主/子 agent 对比、类别柱状图、派单结构、诊断信号、热点派单、版本时间线折线图。
- 给用户汇报时用中文，先给一张「预期 / 旧 / 新 / 是否达到」表，再给「每单元指标」表和「子 agent 成本按类别」表，最后是 2–3 条最值得做的下一步（每条挂一个杠杆编号和预期收益）。不要把整份报告贴进对话。
- 指标口径、分母、等效输入的折算见 references/metrics.md。遇到数字和直觉不符，先查口径。

## 接入新技能

1. 照 references/profile.md 写 `_skill-metrics/<技能名>/profile.json`。
2. `collect.py` 后用 `analyze.py --b all` 看「其他」类别占比，超过 5% 就补分类规则。
3. 用 `version.py register` 登记当前版本作为基线（历史版本有备份可用 `--skill-md`，只有指纹可用 `--no-snapshot --alias-hash`）。

## 平台差异

- **Claude Code**：`~/.claude/projects/<项目>/<会话>.jsonl` + `<会话>/subagents/`。技能每次加载都有正文指纹，能精确归到版本（`--attribution auto`）。
- **Codex**：`~/.codex/sessions/**/rollout-*.jsonl`，子线程靠 `parent_thread_id` 关联，和 `spawn_agent` 调用按时间顺序配对（启发式）。没有加载指纹，按版本生效时间归属。
- 经 OpenAI 网关的子 agent 输出 token 记为 0，比较时只看输入类指标。
