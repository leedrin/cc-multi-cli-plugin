# OpenSpec 常驻审查员 Apply

两个角色：**你**（主 agent）依次做执行者和验收员；**常驻审查员**（子代理 `openspec-resident-reviewer`）审查每一张单、每个阶段和最终交付。除它之外不派任何子代理。

为什么要这样：同一个 agent 写完再审，用的是同一套上下文和盲点，「无发现」不花成本；而审查员独立读 spec、只信执行出来的证据（变异、先红、探针），审得出你自己看不到的问题。工单、回执、PLAN.md 仍然落盘，是续跑和追踪的唯一依据。

工作目录是仓库根下的 `_solo-rv/`，只属于本技能。格式和协议都在本技能的 references/ 里：
- [工单图格式](references/plan.md)、[工单格式](references/ticket.md)、[回执格式](references/receipt.md)、[通用规则清单](references/checklist.md)
- [审查员协议](references/review-protocol.md)（通信、开场/换届、首审/复审、变异安全、探针标准）；报告格式：[工单审查](references/review.md)、[阶段/终审](references/stage.md)
- 脚本（本仓默认在 `.claude/skills/openspec-solo-reviewed-apply/scripts/`，调用写法 `node <路径>/<脚本> <子命令>`，开跑时把实际路径写进 PLAN.md 命令表）：
  - `records.mjs`（下称 **records**）：打印模板，检查工单/回执/审查报告/阶段报告/场景表，巡检整个 `_solo-rv/`，并把报告里的数字和 json 核对。
  - `mutate.mjs`（下称 **mutate**）：变异、先红校验、`status`/`recover`。主要由审查员用；你只在提交前跑 `status`。

## 不间断推进（最高优先级）

目标是**一次调用内**把 `tasks.md` 推进到全部完成。回合只允许在三种情况结束：① 全部完成；② 剩下的单全被 `blocked/` 挡住、无事可做；③ 命中「停下来问」。

- 每张单提交后的那一行消息只是进度标记，不是收尾：发出后紧接着在同一回合里继续下一步。不以「接下来我将……」「要继续吗？」「先到这里」结束回合。
- 不因任务多、上下文长而停下。上下文被压缩后，从文件系统按「续跑」接着做，不凭记忆。
- 遇到问题按顺序处理：自己解决 → 记进假设/存疑后继续 → 单挪 `blocked/` 后做下一张 → 才是停。
- 命令超出前台等待时限被转到后台：等它结束并读输出，不重复启动、不当成失败。
- **等审查员不算停**：送审后在同一回合里轮询落盘文件（见「三」），期间不改工作区也不结束回合。
- 用户让你「停」时才停。

## 少说话（只管聊天，不管文件）

- 只约束对用户说的话：不复述工单、计划、代码、命令输出，不预告下一步。**不适用于落盘的工单、回执、PLAN.md，也不适用于审查员的报告**，它们永远写满。
- 只在三种时候对用户说话：每张单提交后一行 `T<编号> 完成 <短 hash>（审查 <N> 轮；发现 <数>；变异存活 <S>；存疑 <N>）`；命中「停下来问」；全部完成时。
- 开头只说一行「使用 change：<name>，续跑自 <T编号/阶段>，审查员第 <N> 届」或「使用 change：<name>，新拆解」。

## 记录不许缩水（防飘移，最高优先级之一）

上下文压缩或会话变长后，格式文件不在上下文里，记录会越写越短。下面没有例外：

1. **写之前取模板，不凭记忆、不模仿上一张**：`records skeleton ticket|receipt` 取工单/回执模板，整份填全。第 1 张和第 50 张用同一份。
2. **写完立刻检查，不过不往下走**：
   - 工单写完 → `records ticket <工单文件>`
   - 回执每追加一节 → `records receipt <回执文件>`
   - 审查员的报告 → `records review <报告>`（阶段/终审用 `records stage <报告>`）
   - 提交前 → `records receipt <回执文件> --complete`
   - 提交后写完工单「## 记录」→ `records ticket <工单文件> --done`
   - `ERROR` 当场补全直到 `OK`。不得以「已提交/已通过」为由跳过。
3. **审查的「无发现」必须带证据**：records 会拒绝没有 ≥3 条探针（命令 → 结果）的「无发现」，拒绝与 json 对不上的变异统计，拒绝没处置的存活变异。你不得替审查员补探针或改数字。
4. **已完成的工单不改写成指针**：`done/` 里的工单保留完整正文并追加「## 记录」。
5. **合并工单不留占位行**：PLAN.md 每行的「openspec 任务」必须有具体任务号；并入别的单就把原单挪 `dropped/` 并写明并入哪张。
6. **巡检**：每次续跑开头、每个阶段收尾后、全部完成前跑 `records audit`（全部完成前加 `--final`）。`ERROR` 先补齐（能从 git、回执、tasks.md 还原就还原，还原不了写「当时未记录」，不编造）；`WARN` 要打开看一眼。
7. 过程日志、临时脚本放 `_solo-rv/_logs/`；`_solo-rv/` 根下只留 PLAN.md、LESSONS.md 和各状态目录，审查材料在 `_review/`。
8. **没有 Node 时**：records/mutate 跑不了 → 记进 PLAN.md「拆解假设」，改为人工逐项核对 references 末尾的自检清单；审查员仍必须执行探针，只是没有 json 交叉核对，主 agent 在回执写「人工自检：通过」。

## 运行环境

- **权限**：流程要无人值守地执行 git add/commit/status/diff/log/show、项目测试/lint/类型检查、`openspec`、`node`（records、mutate）、读写仓库文件，并**调用且只调用** `Agent(openspec-resident-reviewer)` 与 `SendMessage`。会话须处于免审批模式。
- **前置检查（开跑第一步，只做一次）**：
  1. `.claude/agents/openspec-resident-reviewer.md` 存在；
  2. `.claude/settings.json` / `settings.local.json` 的 `permissions.deny` 里**没有**裸的 `Agent` 或 `SendMessage`（本仓的 `settings.local.json` 为 solo-self 技能写过这两条，会挡住审查员）。有就告诉用户：把这两条从 deny 里删掉，改成 `"Agent(general-purpose)"`、`"Agent(Explore)"` 之类具体的 deny，并在 allow 里加 `"Agent(openspec-resident-reviewer)"`、`"SendMessage"`；这属于「停下来问」里的改权限，改完才继续；
  3. 第一次派单报「找不到 agent 类型」→ 新建的 agent 文件要重新加载：让用户重启会话或 `/agents` 重载后再跑；
  4. 没有 Agent 工具（环境不支持子代理）→ 说明本技能无法运行，建议改用 openspec-solo-self-apply，不要自己扮演审查员冒充。
- **Shell（Windows PowerShell 5.1 也要能跑）**：命令用 `;` 串接，别用 `&&`；看失败检查 `$LASTEXITCODE`。不用 bash 花括号展开、`mkdir -p`、`cat`/`head`/`grep`；读文件用 Read 工具。多行提交信息用多个 `-m`。
- **命令表**：先从 `package.json` scripts、`CLAUDE.md`/`AGENTS.md` 确定单文件测试、按文件 lint、类型检查、全仓门禁、项目特有检查，外加「记录检查」「变异/先红/恢复」两行，写进 PLAN.md 的「命令表」，之后一律照表。「单文件测试」要在一两分钟内跑完，它同时是审查员做变异的命令。
- 依赖缺失 → 装项目声明的依赖，不必问。命令依赖外部条件（缺登录、缺生成物、要联网、付费）→ 只尝试一次；仍不行记「外部阻塞」，改用可用的替代验收并在回执标注，同类命令不再重试。

## 前提与准备

1. 选 change：用户点名就用；否则 `openspec list --json`，只有一个活动 change 就用它，多个就问。
2. `openspec instructions apply --change "<name>" --json`，读 `contextFiles` 和项目规矩。`state` 为 `all_done` → 提示归档并结束；`blocked` → 说明缺哪个 artifact 并停。
3. 确定命令表和分支：当前不在 `main`/`master` 就用当前分支，不新建；在主干上就建 `feat/<change 名>`。
4. 建 `_solo-rv/` 下的 `open`、`doing`、`done`、`blocked`、`dropped`、`_receipts`、`_logs`、`_review`（逐个 `New-Item -ItemType Directory -Force`）。再把 `/_solo-rv/` 追加进 `.git/info/exclude`（已有则跳过）。
5. 工作区已有与本 change 无关的未提交改动时，提醒用户一次：提交只按路径提交本单文件。change 目录没被 git 跟踪时，勾选 tasks.md 不进提交，也不算越界。
6. **启动审查员（开场）**：用 Agent 工具，`subagent_type: openspec-resident-reviewer`，派「开场」（内容见 [审查员协议](references/review-protocol.md) 二）。把返回的 agentId 写进 PLAN.md「审查员」小节（第 1 届）。等 `KICKOFF.md` 首行不再是「进行中」，跑 `records scenarios` 到 `OK`。此后所有派单都用 `SendMessage` 发给这个 agentId，不再新建。
7. 建议在新会话里开跑（提醒一次，不阻塞）。

## 续跑（每次被调用先做）

先看文件系统，不凭记忆。没有 `_solo-rv/PLAN.md` → 进「一」。否则：

1. 重读本文件「记录不许缩水」，跑 `records audit`（`ERROR` 先补齐）。
2. **审查员必须换届**：新会话里旧审查员已不存在，新起一个，派「接班」，更新 PLAN.md「审查员」小节（同一会话内上下文被压缩时，先 `SendMessage` 到 PLAN.md 记的 agentId 试一次，找不到再换届）。
3. 跑 `mutate status`：`DIRTY` → 先 `mutate recover`，再用 `git diff` 看剩下的改动是不是自己写的。
4. 看 `_solo-rv/doing/` 里的单（一次只该有一张），读它的回执**最后一节**：

| 状态 | 续跑位置 |
| --- | --- |
| 工单末尾已有 `提交：` | 「五」收尾里没做完的项 |
| 最后一节是「验收」且通过、无 `提交：` | `git log -5 --oneline` 和 `git status --short -- <文件清单>` 核对：已提交 → 补「记录」并收尾；未提交 → 做提交 |
| 最后一节是「验收」且不通过 | 「四」开修复轮，来源是验收失败项 |
| 最后一节是「审查」或「复审」 | 「四」分诊 |
| 最后一节是「执行」，且 `_review/` 里已有该单报告但回执没链接 | 报告首行不是「进行中」→ `records review` 后补「审查」节；还是「进行中」→ 等它，超时则换届重新送审 |
| 最后一节是「执行」，无报告 | 「三」送审 |
| 最后一节是「修复 <轮次>」 | 「三」送复审 |
| 没有回执 | 「二」执行：先 `git status --short` 看「只动」文件里的半成品，在其基础上接着做 |

`doing/` 为空 → 按 PLAN.md 取下一张前沿单。某阶段的单已全部收尾但没有 `STAGE-<N>.md` → 先做「五·六」阶段审。

## 回执

每张单一个回执 `_solo-rv/_receipts/T<编号>.md`，每阶段结束追加一节。格式见 [回执格式](references/receipt.md)；每次写前 `records skeleton receipt`，追加后 `records receipt`。UTF-8 无 BOM，不要整份重写已有的节。「审查/复审」节只放报告链接、发现数、结论，由 records 与报告互相核对。

## 任务类型与并单

拆解时先给每条任务定类型：

| 类型 | 处理 |
| --- | --- |
| 约定类（如「提交约定」「记录基线」） | 不单独成单，随首张相关单一并勾选 |
| 门禁类（只是「运行全仓检查 / hook 测试」） | 不单独成单，并入同阶段最后一张单的验收，通过后一并勾选；失败了按「五」建修复单 |
| 表征 / 回归锁定类（给现有行为加测试，改动前就通过） | 无先红，审查员的先红校验写「不适用」；它是不是空断言由**变异验证**判定，你不要自己去改源码试 |
| 文档 / 清单 / 记录模板类 | 轻量路径：执行 → 送审（场景映射可「不适用」，变异「不适用」）→ 验收 → 提交 |
| 需要外部条件才能真跑的类（手工 GUI、多版本对比、付费 live、联网演练） | 先做能离线完成的部分；实际执行只试一次；跑不了 → 单挪 `blocked/`，tasks.md 里**不勾选**，任务行末追加 `⏸ 待外部条件：<原因>`。不要为了「全部完成」而勾选没做的事 |
| 代码类 | 正常走「二」到「五」 |

## 一、拆解：写 PLAN.md

读完 `proposal.md`、`design.md`、`specs/`、`tasks.md` 和 SCENARIOS.md，自己摸代码（要改的模块、入口、契约类型、测试命令和 fixture）。只读需要的片段。

- 一张单是一条能独立验证的纵切路径。需要先重构或补测试脚手架的放最前面单独成单。
- 尺寸：以 tasks.md 的 `## N` 任务组为主线（`## N` 的 N 填进 PLAN.md 的「阶段」列），一张单可覆盖相邻、验收相同的几条小任务（≤6 条）；通常改动 ≤5 个文件、验收 ≤4 条命令。
- 验收命令改动前会失败、改动后通过；用只作用于本单文件的形式，加一次类型检查。
- **场景要认领完**：SCENARIOS.md 的每个场景都要被某张单的「场景」字段认领，或在拆解假设里说明归属（外部类）。`records audit` 会列出无人认领的场景，终审时是 ERROR。
- 「必须保持」里「不改变既有行为」的条目，验收里要有测试锁住。
- 全仓门禁里若有「死代码/未使用导出」检查：新模块的导出必须在同一张单里被测试或调用方引用。
- 新模块的单先建导出桩（抛 `not implemented`），让「先红」红在断言上。
- 依赖只连真正卡住的边；编号顺序就是施工顺序。

模糊点自己拿主意：design 已定 → 照做；spec scenario 能推出 → 照推；代码惯例 → 跟随；都没有 → 选改动最小、最易回退的，记进「拆解假设」。

写 PLAN.md 后自检：tasks.md 每个未勾选任务都被某张单覆盖或明确归入「随单勾选/外部条件」；每张单有确定的「只动」、能失败的验收、认领的场景；无环。

## 一·五、写工单

**一次只写下一张单**。先跑 `records skeleton ticket` 取模板，整份填全后写到 `_solo-rv/doing/T<编号>-<短名>.md`，立刻 `records ticket <文件>` 到 `OK`；PLAN.md 该行改「进行中」。「场景」填本单认领的 SCENARIOS.md 编号（审查员会核对你有没有漏列）。「必须保持」写成能检查的条目并标出处。

## 二、执行

1. 读工单、它列出的文件、`_solo-rv/_review/MEMORY.md` 的「复发缺陷」（存在时）、`_solo-rv/LESSONS.md`、清单里适用的小节。这些是审查员以往抓到的问题，别再犯。
2. **先红**（表征/文档类按「任务类型」）：先写测试，运行，确认失败，把关键失败行写进回执草稿。
3. 实现，只动「只动」里的文件。按工单走不通 → 回执状态写「中断」，进「六」。
4. **后绿**：跑工单全部验收命令。报错全部落在本单以外、已有未提交改动的文件里 → 记「外部阻塞」。
5. 追加回执「## 执行」，`records receipt` 到 `OK` 才进「三」。

## 三、送审（交给常驻审查员）

1. **前置**：工作区除本单文件外无半成品；`mutate status` 为 `CLEAN`；回执「执行」已过 records。
2. `SendMessage` 给审查员，内容按 [审查员协议](references/review-protocol.md) 三：工单编号、轮次（首审 r1，复审 r2…）、落盘文件 `_solo-rv/_review/T<编号>-r<轮次>.md`、工单和回执路径、命令表里的单文件测试命令、实现文件清单；复审另附要核对的条目。
3. **等**：每 20 秒读一次落盘文件的第一行（`Start-Sleep -Seconds 20` 之间），**期间不改工作区、不提交**（变异在原文件上临时改动）。第一行不再是「进行中」才算写完；超过 20 分钟仍在「进行中」→ 先 `mutate recover` + `mutate status`，再按「续跑」换届重新送审。
4. 审查员回复后：`mutate status` 必须是 `CLEAN`（不是就 `mutate recover`）；`records review <报告>` 到 `OK`（有 `ERROR` 把输出原样发回审查员补，最多 3 次，仍不过 → 单挪 `blocked/`，原因写「审查报告不合格」）。
5. 追加回执「## 审查」（复审为「## 复审 <轮次>」）：审查报告路径、发现数、结论，`records receipt` 到 `OK`。

## 四、分诊与修复轮

- 结论「进验收」→ 「五」。结论「阻塞」→ 按「六」处理。
- 发现逐条分诊：「超范围」→ 不修，记进后续单或存疑；「改 spec」→ 不停下来问：采用改动最小、最易回退的解读，在 `design.md` 末尾「实施期决策补充」记一条（写清依据），继续。
- **收敛**：从 c 轮起，类型「测试」的中/低发现不再开轮，结论记「存疑：测试 <编号>」后进「五」（但先红为绿、场景缺口、杀不死的变异不算「可存疑」，必须修）。
- 其余 → 开修复轮（b、c、d、e），不写新工单。可改文件 = 「只动」+ 发现点名的文件及其直接测试。逐条：
  1. **先找根因，再改**：从症状出发，沿逻辑链和数据链梳理，并**对照原版**（基线 / `upstream` 同名文件 / spec 与 design 原文）看哪里不一致；没找到根因前不加兜底、补偿或吞错。写能复现的测试并运行，失败关键行记下；复现不了才可判「不成立」，且必须附**可再跑的证据命令**，是否接受由复审裁决。
  2. 按类修：grep 同类写法，一并修，列出查过的位置。
  3. 后绿：同一测试通过，并重跑工单全部验收命令。
- 追加回执「## 修复 <轮次>」，`records receipt`。**修复之后一律送复审**（回「三」，轮次加一），改完不能自己放行。
- 某类问题在别的单也出现过，或属于清单没覆盖的通用坑 → 往 `_solo-rv/LESSONS.md` 追加一行 `- <类别>｜<规则>｜出处 T<编号>`。

**上限**：每张单最多 4 个修复轮。第 4 轮复审仍不是「进验收」时**不停下来问**：回执写「## 卡住」（症状、根因分析、试过什么、建议），单挪 `blocked/`，PLAN.md 改「阻塞」，继续下一张不依赖它的单。只有剩下的单全都依赖它时才结束回合。

## 五、验收、提交、收尾

验收是你的一次独立重跑，不引用执行时或审查员的结果：

1. 工单「验收」里每条命令原样重跑；再跑命令表里的类型检查和 lint。报错全部落在本单以外、已有未提交改动的文件 → 外部阻塞，不算失败。
2. 越界：`git status --short` + `git diff --stat`，本单产出必须都在允许范围内。
3. 测试篡改：`git diff -- <测试文件>`，查有没有删测试、放宽断言、加 skip。
4. 工作区：`mutate status` 必须输出 `CLEAN`，照抄进回执「工作区」。
5. 追加回执「## 验收」。不通过 → 回「四」，来源是验收失败项。

通过后：
0. 提交前门：`records receipt <回执文件> --complete` 必须 `OK`。
1. `git add <本单产出的每个文件>`，`git commit -m "<摘要>" -- <同一批文件>`。提交信息风格：change 的 design/proposal 给了提交序列就用那里的格式；没给就跟随 `git log` 近几条。不在提交信息里写工单编号。`_solo-rv/` 下的文件不进提交。不许 `git add -A` / `.`。绝不在 `main`/`master` 上提交。
2. 提交后核对：`git show --stat --name-only HEAD` 的文件集合等于本单文件清单；不等先修正（`git commit --amend` 仅限刚做的这一次提交）。
3. 工单末尾追加「## 记录」（提交、验收、修正、存疑，格式见 [工单格式](references/ticket.md)），`records ticket <工单文件> --done` 到 `OK`。
4. 工单挪 `_solo-rv/done/`（整份保留）；PLAN.md 改「完成」；`tasks.md` 勾掉本单覆盖的每条任务；按需追加 LESSONS.md。
5. **阶段门禁**：一个阶段的最后一张单收尾后，跑 `records audit` 和命令表的全仓门禁，通过后进「六·阶段审」。门禁失败且问题属于本 change → 新建一张修复单（编号顺延，走完整流程）；失败全落在本 change 之外的未提交文件 → 记外部阻塞，继续。
6. 对用户说一行完成消息，**然后立刻回「一·五」写下一张单**。

## 六、阶段审与终审

- **阶段审**：阶段内所有单「完成」或「放弃」后，`SendMessage` 派「阶段审」（阶段号、本阶段完成的 T 编号及提交 hash、落盘 `_solo-rv/_review/STAGE-<N>.md`）。等待方式同「三」，`records stage <报告> --expect <T编号,…>` 到 `OK`。结论「开修复单」→ 新建修复单（阶段号相同、编号顺延、走完整流程），修完后重新阶段审，覆盖该报告。
- **终审**：见「全部完成时」。
- **审查员放水抽查**：`records audit` 报「全是无发现」的 WARN 时，挑一张已完成的单，自己跑 `mutate run --files <它的实现文件> --lines all --cmd "<它的测试命令>"`，把存活的变异（等价的除外）用 `SendMessage` 发给审查员，要求写进 MEMORY.md 并说明为什么首审没抓到；这不替代审查员的判断，只是校准。

## 七、中断

- 工单写错或太大 → 改写或拆分；原单挪 `dropped/` 并在末尾写 `原因：…`（并入别的单写明并入哪张），PLAN.md 同步为「放弃」。
- 缺外部条件 → 挪 `blocked/`，末尾写清 `原因：…`，PLAN.md 同步为「阻塞」，继续下一张不依赖它的单。
- 暴露设计问题 → 小澄清直接更新 `design.md`/`specs/` 并在最终总结里说明；改变范围、行为或接口的按「四」处理，不停下来问。

## 停下来问

只在这些时候问用户：删数据、删目录、强推、`push`、对外发消息等不可逆或对外可见的操作；安装全局软件或改模型/effort；**改权限设置（前置检查里的 Agent/SendMessage deny）**；多个活动 change 选不出；剩下的单全被外部条件挡住；与 proposal/design 的 Non-Goals 或用户硬约束直接冲突。其余都自己拿主意并记进 PLAN.md 或回执。

## 全部完成时

1. 派「终审」给审查员（落盘 `_solo-rv/_review/FINAL.md`，列全部完成的 T 编号），`records stage <报告> --expect <全部完成的 T 编号>` 到 `OK`；结论「开修复单」→ 建修复单走完，再终审。
2. `records audit --final`，`ERROR` 必须清零（补不了的按「记录不许缩水」第 6 条注明）。
3. `openspec instructions apply --change "<name>" --json` 的 `progress.remaining` 为 0，或剩余的任务全带 `⏸ 待外部条件` 且对应单在 `blocked/`。**以这个命令的结果为准，不以 PLAN.md 为准**；有未勾选且不属于上述两类的任务 → 回「一」补拆，不结束。
4. 用大白话、按用户能感知的功能说：现在能用了什么；用户可能注意到的变化；还剩的风险（存疑、审查员没覆盖到的地方、`blocked/`/`dropped/` 里的单及原因、外部阻塞的检查）；拆解时替用户做的判断；审查质量（共几份报告、发现总数、变异总数与存活处置情况）；建议归档（openspec-archive-change）。

## 规矩

- 用用户的语言汇报。
- 子代理只有一个：常驻审查员，只在会话开始时新建（换届除外）；不派别的子代理，不请它写代码、改工单。
- 工单和回执永远写满，每次从 records 的模板起笔。
- 审查员的结论由 records 核对：不替它补探针、改统计、改报告内容；它报告写不对就退回给它。
- 变异进行时不碰工作区；提交前 `mutate status` 必须 CLEAN。
- 密钥不写进代码、工单、回执、日志和报告。
- 不 push；自检时起的后台进程收尾前关掉。
- 一次只做一张单，前一张提交并收尾后才开下一张。
