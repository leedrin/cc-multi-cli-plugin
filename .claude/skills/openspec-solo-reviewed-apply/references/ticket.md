# 工单格式

用于拟定前沿工单，写进 `_solo-rv/doing/`。创建时机和内容要求见 SKILL.md「一·五、写工单」。修复轮不写工单文件，原工单即依据；通用规则见 [checklist.md](checklist.md)。

```markdown
# T<编号>：<简短标题>

- openspec：<change 名> / 任务 <如 2.1、2.2>
- 类型：<代码 / 表征 / 文档 / 外部>
- 被谁阻塞：<已完成的 T 编号，或「无」>
- 场景：<本单要实现的 SCENARIOS.md 编号，如 S003, S004；只有文档/外部类才能写「无」>

## 目标
<一句话：完成后用户/调用方能观察到什么行为。>

## 动手前先读
- <项目规矩、相关 spec requirement/scenario、design 决定、要改的文件>
- <前置工单已产出、这张单要用到的东西（接口名、文件）>

## 边界
- 只动：<文件 / 模块>
- 适用通用规则：<路径 / 密钥 / 并发 / SQL 中涉及的几类；都不涉及写「无」>
- 必须保持：<design 里不能动摇的决定、要兼容的已有行为；引用章节里与本单相关的硬规则逐条列出并标出处，如「03 §7.1：每个 retriever 对同一 chunk 最多贡献一次」>

## 验收
1. `<命令表里的命令，带本单的文件>` → <预期结果>
（阶段最后一张单：加一条命令表里的全仓门禁。）

## 为什么这样验收
<这些检查要保住的真实目的，引用 spec scenario。变异验证和先红校验由审查员做，这里不用写。>
```

## 写法要求

- 模板以 `node <技能目录>/scripts/records.mjs skeleton ticket` 的输出为准（就是上面这个代码块）。每张单都重新取一次，不要照上一张单改，也不要凭记忆写。
- 「场景」是审查员核对「你有没有漏做」的独立依据：编号来自审查员开场时从 specs/ 列出的 `_solo-rv/_review/SCENARIOS.md`。tasks.md 里本单覆盖的任务对应的场景要列全，漏列会被首审报成发现。
- 写完跑 `records ticket <工单文件>`；收尾后跑 `records ticket <工单文件> --done`。
- 工单正文是日后追踪「当时为什么这么做、边界是什么」的唯一依据：任何阶段都不得缩写成「已完成，见回执」，挪进 `done/` 时整份保留。
- 尖括号 `<…>` 里的提示文字必须替换掉，不得残留。

收尾时在工单末尾追加（`--done` 会检查）：

```markdown
## 记录
- 提交：<hash>
- 验收：通过（重跑 <N> 条命令）
- 修正：<如「b（审查 1、2）」或「无」>
- 存疑：<最多 3 条，没有写「无」>
```

挪出主线的工单（`blocked/`、`dropped/`）末尾必须有一行 `原因：<…>`（blocked 写在等什么；dropped 写原因，并入别的单要写明并入哪张）。

## 人工自检清单（仅在 records 跑不了时使用）

- [ ] 首行 `# T<编号>：<标题>`，头部有 openspec、类型、被谁阻塞、场景
- [ ] 小节依次齐全且非空：目标、动手前先读、边界、验收、为什么这样验收
- [ ] 边界含：只动、适用通用规则、必须保持
- [ ] 验收是编号的命令列表
- [ ] 完成后有「## 记录」：提交 hash（`git cat-file -e <hash>` 能通过）、验收、修正、存疑
- [ ] 没有残留的 `<…>` 提示文字
