# 工单审查报告格式（审查员写）

每次审查一份：`_solo-rv/_review/T<编号>-r<轮次>.md`（首审 r1，复审 r2、r3…）。变异和先红校验的机器输出放在同目录：`T<编号>-r<轮次>.mut.json`、`T<编号>-r<轮次>.base.json`。完成前第一行写 `进行中 @<时间>`，全部写完后整份覆盖成下面的格式（第一行不再是「进行中」）。

```
# 审查报告 T<编号> 第<轮次>轮｜<日期时间>

- 类型：<首审 / 复审>
- 工单类型：<照抄工单头部的类型：代码 / 表征 / 文档 / 外部>
- 范围：<被审的文件清单（以 git status 为准）；复审写要核对的条目编号>

## 场景映射
- S<编号>｜<测试名，原文，要能在测试文件里搜到>｜<测试文件:行号>｜<覆盖 / 缺口>
<文档/外部类单改写成「不适用：<≥8 字理由>」；缺口没有测试时测试名和文件写「无」>

## 先红校验
结果：<红 / 绿 / 不适用：<理由>>
命令：<baseline 命令> → <旧实现下失败的关键 1–3 行>
报告文件：<_solo-rv/_review/T<编号>-r<轮次>.base.json>

## 变异
<贴 mutate.mjs run 的汇总行（变异：N 个，杀死 …），或改写成「不适用：<≥8 字理由>」>
报告文件：<_solo-rv/_review/T<编号>-r<轮次>.mut.json>
处置 <变异 id>：<杀不死 / 等价（理由）>

## 探针
1. <亲手执行的命令> → <结果> → <它能推翻哪个结论>

## 发现
<N. 严重程度｜归属｜类型｜文件:行号｜问题｜代码证据｜怎么改；或 无发现（查了什么：…）>

## 结论
结论：<进验收 / 开修复轮 <轮次> / 阻塞>，<一句话理由>
```

## 写法要求

- 模板以 `node <技能目录>/scripts/records.mjs skeleton review` 的输出为准；写完跑 `records review <报告>` 到 `OK` 才算写完。
- 模板里整行的 `<…>` 提示（如「文档/外部类单改写成…」「处置 <变异 id>：…」）要么替换成真实内容，要么整行删掉；残留会被 `records review` 当占位符报错。
- **场景映射**：从工单头部的「场景」和 SCENARIOS.md 里属于本单任务的场景出发，逐条找到断言它的测试和行；找不到记「缺口」并成一条发现。工单漏列的场景也记一条发现。测试名必须是测试文件里的原文，`records review` 会去文件里搜。
- **先红校验**：`mutate.mjs baseline` 把实现文件换回 HEAD 版本（新文件换成空文件）再跑本单测试，必须红。结果「绿」表示测试没测到新行为，必须有发现。表征/文档类写「不适用：<理由>」。
- **变异**：汇总行和 json 必须来自 `mutate.mjs run`，`records review` 会逐项核对；每个存活变异都要有「处置」：杀不死 = 测试缺口 = 一条发现；等价 = 改了不影响任何可观察行为，写出为什么。
- **探针**：每条是你亲手跑过、结果可能与预期相反的命令，格式「N. 命令 → 结果 → 说明」。「无发现」至少 3 条探针；有发现也要有 1 条以上。
- **发现**每条 7 段，严重程度高/中/低，归属本单/超范围/改 spec，类型缺陷/测试；没有证据的怀疑不写成发现，写进探针里去验证。
- **结论**：有「高/中｜本单」的发现不能写进验收；没有发现不能写开修复轮。
