# 回执格式

每张单一个回执文件 `_solo-rv/_receipts/T<编号>.md`。每个阶段结束时**追加**一节，不覆盖前面的节；节标题照下面原样写，续跑靠最后一节判断位置。审查的完整内容在审查员的报告里，回执的「审查/复审」节只做链接并抄下结论，两边由 `records receipt` 互相核对。

```
## 执行
状态：完成 / 中断
文件清单：<本轮改动和新建的全部文件>
先红：<测试名> → <修复前失败的关键 1–5 行>
      （表征/文档类写「不适用：<类型>」）
验收：<命令> → 通过/失败/外部阻塞（失败时附关键报错 ≤10 行）
存疑：<没有写「无」>

## 审查          （复审写「## 复审 <轮次>」）
审查报告：<_solo-rv/_review/T<编号>-r<轮次>.md>
发现数：<报告「发现」小节的条数，无发现写 0>
结论：<进验收 / 开修复轮 / 阻塞，照抄报告>

## 修复 <轮次>
来源：<审查/验收> 条目 <编号…>
<编号｜成立·已修（测试名）/ 不成立（可运行的证据）｜根因：<症状 → 逻辑/数据链 → 与原版不一致处>｜同类位置：<列表或「无」>>
先红：<每条成立的修复前失败关键行>
文件清单：…
验收：…

## 验收
<命令 → 通过/失败/外部阻塞>
越界：<通过 / 越界文件>
测试篡改：<无 / 具体位置>
工作区：<CLEAN，照抄 mutate.mjs status 的输出>
结论：通过 / 不通过（失败项编号）

## 卡住          （修复轮到上限时写；单随即挪 blocked/）
症状：…
根因分析：<逻辑链 / 数据链 / 与原版的差异；没找到就写「未找到」>
试过：…
建议：<改方案 / 拆任务 / 改 spec / 放弃>
```

每节写完再进下一阶段。阶段做了一半被打断时，续跑从上一节的状态重来这个阶段。

## 写法要求

- 模板以 `node <技能目录>/scripts/records.mjs skeleton receipt` 的输出为准（就是上面第一个代码块）。每次写回执都重新取一次，不要照前一张回执改，也不要凭记忆写。
- 每节追加后跑 `records receipt <回执文件>`；提交前跑 `records receipt <回执文件> --complete`（要求：有审查、最后一次审查/复审的结论是「进验收」、每次修复之后有复审、最后一节是通过的验收且工作区 CLEAN）。
- 「审查/复审」节引用的报告必须存在、通过 `records review`，发现数和结论要与报告一致；报告还是「进行中」时不能写这一节。
- 修复轮里判某条发现「不成立」，必须附能再跑一遍的命令或测试作为证据；是否接受由下一轮复审判定，不由你自己说了算。
- 同一行写多个字段可以（如 `越界：通过；测试篡改：无`），但字段名和冒号不能少；`验收` 节要有 `命令 → 结果` 的逐条记录。
- 文件用 UTF-8（无 BOM 更好），尖括号 `<…>` 里的提示文字必须替换掉，不得残留。
- 命令输出只写结论和关键报错，但**字段不能省**。「少说话」只管对用户的聊天，不管本文件。

## 人工自检清单（仅在 records 跑不了时使用）

- [ ] 第一节是「执行」，含：状态、文件清单、先红、验收、存疑
- [ ] 每个「审查/复审」含：审查报告路径（文件存在且不是「进行中」）、发现数、结论
- [ ] 每个修复轮含：来源、先红、文件清单、验收；每条成立的发现写了根因
- [ ] 每次修复之后都有复审；最后一次审查/复审结论是「进验收」
- [ ] 最后一节是「验收」：命令 → 结果、越界、测试篡改、工作区 CLEAN、结论：通过
- [ ] 没有残留的 `<…>` 提示文字
- [ ] 回执末尾补一行「人工自检：通过」
