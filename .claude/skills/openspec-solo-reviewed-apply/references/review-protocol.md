# 常驻审查员协议

主 agent 和审查员（`openspec-resident-reviewer`）共用这份协议。审查员从会话开始存活到会话结束，审**所有**工单、每个阶段一次跨单审查、最后一次终审。目的只有一个：让「没问题」必须有被执行过的证据，而不是一句判断。

## 一、通信：文件握手

- 所有产出写文件，聊天里只回 ≤15 行摘要。每次派活都给出**落盘文件**路径；审查员开工第一件事是往它写一行 `进行中 @<时间>`，写完后整份覆盖，第一行不再是「进行中」。
- 主 agent 等待时只读文件、**不改工作区**（变异会在原文件上临时改动，见「四」）。每 20 秒读一次落盘文件的第一行，不再是「进行中」就算写完；超过 20 分钟仍是「进行中」，先跑 `mutate.mjs recover` 和 `status`，再换届。
- 报告写完后主 agent 跑 `records review|stage <报告>`；有 `ERROR` 就把输出原样发给审查员要求补，最多 3 次；仍不过，单挪 `blocked/`，原因写「审查报告不合格」。不要自己替审查员补探针或编造结果。

## 二、开场与换届

**开场**（会话第一次启动）派单内容：change 名、仓库根、`_solo-rv/` 路径、落盘文件 `_solo-rv/_review/KICKOFF.md`。审查员要做：

1. 读 `proposal.md`、`design.md`、`tasks.md`、`specs/` 全部，以及 `AGENTS.md`/`CLAUDE.md` 的验证与代码风格规矩。
2. 写 `_solo-rv/_review/SCENARIOS.md`：每个 spec scenario 一行 `- S<三位编号>｜<spec 文件路径>｜<场景名>｜<一句话 WHEN → THEN>`，编号从 S001 起按 specs 目录顺序排。**这份表是独立的验收依据，不看任何实现代码，也不参考主 agent 的拆单。**
3. 写 `_solo-rv/_review/MEMORY.md`（格式见「六」）。
4. 在 KICKOFF.md 写：场景总数、每个 spec 文件的场景数、读了哪些文件、对 spec 本身的疑问（矛盾、无法测试的场景）。跑 `records scenarios` 到 `OK`。

**换届**（SendMessage 找不到原审查员、超时、或会话重启后）：新起一个审查员，派单写「接班」。它读 SCENARIOS.md、MEMORY.md 和 `_review/` 里最近 5 份报告，不重建 SCENARIOS.md，在 KICKOFF.md 末尾追加一行「第 N 届接班：<时间>」。主 agent 同步更新 PLAN.md 的「审查员」小节。**换届不改变任何已出的报告，也不重审已完成的单。**

## 三、首审与复审（每张工单）

**派单内容**：工单编号、轮次、类型（首审/复审）、落盘文件 `_solo-rv/_review/T<编号>-r<轮次>.md`、工单和回执路径、命令表里的单文件测试命令、实现文件清单（先红校验用）。复审另给「要核对的条目」。

首审步骤（顺序固定）：

1. 读工单、回执「执行」节、SCENARIOS.md 里本单场景、MEMORY.md 的「复发缺陷」、工单「适用通用规则」对应的 `references/checklist.md` 小节。
2. `git status --short` 与 `git diff -- <文件>` 取真实改动范围，核对回执的「文件清单」：多了或少了就是一条发现。
3. **场景映射**：逐条列出本单场景及 tasks.md 里本单任务对应的所有场景，找到断言它的测试与行；找不到记缺口。
4. **先红校验**（代码类）：`node <技能目录>/scripts/mutate.mjs baseline --impl <实现文件> --cmd "<测试命令>" --out _solo-rv/_review/T<编号>-r<轮次>.base.json`。必须红；绿 = 发现。
5. **变异**：`node <技能目录>/scripts/mutate.mjs run --files <实现文件> --cmd "<测试命令>" --out _solo-rv/_review/T<编号>-r<轮次>.mut.json`（默认只变异本单新增行，最多 24 个，总预算 15 分钟）。逐个处理存活变异：读变异前后的代码，能说清「改了之后任何可观察行为都不变」才判等价，并写出理由；否则判杀不死，成一条「测试」类发现。
6. **探针**：至少 3 条自己设计并亲手跑的检查，每条可能推翻你的结论（见「五」）。
7. 读代码找缺陷：逻辑边界、误伤已有数据、安全（路径越界、密钥外泄、绕过审批）、稳定性（并发、超时、资源释放）、与工单「必须保持」的一致性。只写有证据的，不写风格建议。
8. 写报告（格式见 [review.md](review.md)），跑 `records review <报告>` 到 `OK`，再回摘要。**回摘要前确认 `mutate.mjs status` 为 CLEAN。**

复审：先核对「要核对的条目」是否真正闭合、同类位置是否修全、修复前失败的测试是否锁得住；然后整套重跑 3–6 步（变异按 diff 重新取点），因为修复本身可能引入新问题。新发现只报落在本轮改动行上的。

**对「不成立」的裁决**：主 agent 对某条发现判不成立并附证据命令时，复审里**重跑那条证据**；证据成立则在报告里写「条目 N：接受不成立（证据复跑结果）」，不成立的证据则维持原发现并升一级严重程度。

## 四、变异的安全规则

`mutate.mjs` 会在源文件上逐个改动、跑测试、恢复，原件先备份到 `_solo-rv/_review/.mutation-backup`，每次恢复后校验 sha256，进程退出和 Ctrl-C 时也会恢复。

- 变异运行期间主 agent 不得编辑任何被变异的文件，也不得提交；审查员不得并行启动两个 `mutate.mjs`。
- 提交前主 agent 必须跑 `mutate.mjs status` 得到 `CLEAN`；`DIRTY` 先 `recover`，再核对 `git diff` 是不是自己写的内容。
- 变异命令只给**单文件测试**，不给全仓门禁；测试要在一两分钟内跑完，否则预算耗尽会出现「未试」。
- `mutate.mjs` 报 exit 3（基线本身就红）：说明本单测试现在就不通过，不是变异的问题，回报主 agent 先修。

## 五、什么算探针

探针 = 你亲手执行、结果可能与你的预期相反的命令。记成「命令 → 结果 → 说明」。例：

- `rg -n "<本单新增符号>" plugins test` → 只有 2 处调用，没有未覆盖的调用方 → 调用方完整。
- 把 spec scenario 的输入手工喂给被测入口（`node -e` 一次性脚本，放在 `_solo-rv/_logs/`，不写进仓库）→ 输出与 THEN 一致。
- 单独跑本单的每个测试文件、再把它们按不同顺序合并跑一次 → 都通过，没有顺序依赖。
- `git diff -- <测试文件>` → 没有删除用例、没有放宽断言、没有 skip。
- 读到的一个疑点，用最小命令验证它（而不是写成猜测）。

「看了代码觉得没问题」不是探针。没有可执行的验证手段时，写成「存疑」类发现，说明该补什么测试。

## 六、MEMORY.md

审查员自己的长期记忆，换届和上下文压缩后靠它恢复。每次审查结束后更新，格式固定：

```
# 审查员记忆
## 状态
- 当前届：<N>；已审：<T 编号列表>；进行中：<无 / T 编号>
## 复发缺陷
- <类别>｜<规则一句话>｜出处 T<编号>
## 审查记录
- T<编号> r<轮次>｜发现 <N>｜变异 <杀死>/<总数>，存活 <S>（等价 <E>）｜一句话教训
```

「复发缺陷」只记出现 ≥2 次、或属于清单没覆盖的通用坑；主 agent 执行每张单前会读这一节。

## 七、阶段审与终审

派单内容：阶段号（终审写「全部」）、本阶段完成的 T 编号及各自提交 hash（取自工单「记录」）、落盘文件 `_solo-rv/_review/STAGE-<N>.md` 或 `FINAL.md`。格式见 [stage.md](stage.md)。

只审单与单之间：接口一致、重复实现、死代码、场景覆盖、共享状态（终审再加任务覆盖）。把本阶段所有单的测试文件合并跑一次作为一条探针；场景覆盖用 SCENARIOS.md 对照各单场景字段和测试。发现落在已提交单上的，结论写「开修复单」，由主 agent 新建一张编号顺延的修复单。

## 八、审查员的边界

- 只写 `_solo-rv/_review/` 下的文件和 `_solo-rv/_logs/` 里的一次性探针脚本；不改代码、测试、工单、回执、PLAN.md、tasks.md；`mutate.mjs` 是唯一允许暂时改动源文件的途径。
- 不执行 `git add/commit/checkout/restore/stash/reset/clean`；不 push；不跑全仓门禁（主 agent 的阶段门禁负责）。
- 不派生子代理。密钥不写进任何文件。
