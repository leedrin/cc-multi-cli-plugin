# 第零步：第一次使用，摸清这台电脑

项目里没有 `_tickets/workers.md` 时，先做这一步，做完再接活。已有 workers.md 就直接照它派单，不重新摸；用户换工具或想改选择时再重来一遍。

这一步的目的：以后每次派单都用一条**试跑过的**命令，而不是凭记忆拼参数。CLI 参数经常随版本变化，拼错的代价是一张单白跑几十分钟，或者工人拿到了超出预期的权限。

## 1. 看环境

确认操作系统和你正在用的终端（bash / zsh / PowerShell）。之后所有命令按这个终端的写法来。

Windows 上注意：npm 装的 CLI 在 Git Bash 里可能因为 shim 问题跑不起来，在 PowerShell 里正常。哪个终端能跑就记哪个。

## 2. 找工人

检查这台电脑上装了哪些 AI 命令行工具。常见的有 `cursor-agent`、`agy`、`codex`、`gemini`、`claude`、`pi`、`opencode`、`aider`、`qwen`，也可能还有别的。用终端自带的方式查：

- bash / zsh：`command -v codex claude gemini ...`
- PowerShell：`Get-Command codex, claude, gemini, ... -ErrorAction SilentlyContinue`

一个都没找到（或用户想换一个）→ 看下面「没有工人时」。

## 3. 读说明书

对每个找到的工具跑 `--help`（以及子命令的 help，如 `codex exec --help`），弄清四件事：

1. **无头模式**：怎么不进入对话、一次性执行一句任务；提示能不能从 stdin 读（长提示走文件更稳）。
2. **免确认**：怎么让它不逐项询问、直接改文件和跑命令；有没有沙箱档位（只写工作区 vs 全盘放开），优先选最窄的够用档位。
3. **模型**：怎么指定模型，有没有列出可用模型的命令。
4. **只读模式**：有没有只读或禁用写工具的方式（给审查用）。

**不要凭记忆写参数，以帮助里写的为准。** 帮助里意思拿不准的参数先记下来，到第 5 步试跑时看它实际怎么表现。

## 4. 向用户汇报，让用户来定

用大白话简短列出：找到了哪些工具、各自能用哪些模型。然后请用户决定下面几件事，**一次问一件，等他答了再问下一件**（用 AskUserQuestion）：

1. 谁来施工，谁来审查。建议审查和施工来自不同厂商（不同模型看同一段代码更容易发现盲点），但由用户定。默认建议：施工 codex / gpt-6-luna，审查 claude / sonnet。
2. 各用什么模型。
3. 哪些工人可以看这个项目的代码和数据。各家的隐私条款不同，只有用户能判断。
4. 提醒一件事：让工人「直接改文件、不逐项询问」，意味着它在这个项目里可以不经确认就动手。要用户**明确同意**。

## 5. 试跑一次

征得用户同意后（会花一点额度），给每个选中的工人派一张很小的练习单：

- 在临时文件夹（如 `_tickets/_trial/`，或 scratchpad）里写一个小函数和它的测试；
- 照正式流程走：写工单 → 施工命令 → 等它结束 → 读回执 → 自己重跑验收；
- 审查者用只读审查命令审这张练习单，并确认它**真的没改文件**（`git status` / 比对文件修改时间）。

确认三件事：命令真的能跑通、会按模板写回执、用时大概多少。失败就对照帮助调整参数再试，调到能跑通为止；调不通就如实告诉用户。练习用的临时文件收尾时删掉（这是你自己建的，删前确认路径）。

## 6. 写下来

把结果照 `templates/workers.md` 写进 `_tickets/workers.md`。以后派单都照这里写的命令来。

## 本机已验证过的写法（参考，仍以 --help 为准）

以下在 Windows 10 + PowerShell、codex-cli 0.155.1、Claude Code 2.1.283 上核对过帮助文本，换版本要重新核对：

```powershell
# 施工：codex，无头 + 只写工作区沙箱 + 指定模型，提示从 stdin 读（末尾的 -），最终回答写到 -o 文件
Get-Content <提示文件> -Raw | codex exec -m <模型> -s workspace-write -C <作业目录> -o _receipts/<工单名>.last.md - 2>&1 | Tee-Object -FilePath _receipts/<工单名>.run.log

# 审查：codex 只读沙箱
Get-Content <提示文件> -Raw | codex exec -m <模型> -s read-only -C <作业目录> -o _receipts/<工单名>.review.md -

# 审查：claude，无头 + 禁用写工具 + 放行验收要用的命令
Get-Content <提示文件> -Raw | claude -p --model sonnet --disallowedTools "Edit,Write,NotebookEdit" --allowedTools "Bash(bun test:*),Bash(git status:*),Bash(git diff:*)" | Out-File -Encoding utf8 _receipts/<工单名>.review.md
```

试跑踩过的坑：

- `claude -p` 无头时 Bash 命令默认要人工批准，没人批准就跑不了，审查者只能「手动推演」。要用 `--allowedTools` 把验收命令（测试、typecheck、lint、git 只读命令）放行，否则审查者无法核对回执。
- codex 会继承 `~/.codex/config.toml` 的推理强度；设成 xhigh 时一张小练习单也要十几分钟。把试跑用时写进 workers.md，让用户知道预期，是否调低由用户定。
- 施工日志里的 `Model metadata ... not found` 只说明本地没有该模型的元数据，模型能不能用以试跑结果为准。

## 没有工人时

大多数人第一次用时电脑上一个工人都没有。这时由你帮用户选好、装好：

1. **列选项**：先上网查清楚当前情况，再用大白话告诉用户几类选择，每类说清是哪家的、怎么收费（包在订阅里，还是按用量付费）、隐私条款在哪看。常见的几类：
   - 编程工具自带的命令行版，比如 Cursor 的 cursor-agent，用该工具的订阅额度；
   - 大厂出的命令行工具，比如 OpenAI 的 Codex CLI、Google 的 Gemini CLI；
   - 开源命令行工具配按量付费的模型，比如 pi、opencode、aider 配 DeepSeek、GLM、通义千问，需要用户自己去模型平台开账号、充值、拿 API Key。

   可以给建议，但由用户选。隐私和数据会不会被拿去训练，以各家条款原文为准；查不清的就说查不清，不要替厂商打包票。
2. **说清要装什么**：用户选定后，找这个工具**官方**的安装说明（官网或官方仓库，不用第三方转载），告诉用户要装什么、从哪里下载、用什么命令装。用户明确同意后再装。
3. **装好、验证**：装完跑一下它的 `--help`，确认能用。装失败就把报错如实告诉用户，不要换别的来路硬装。
4. **登录和密钥让用户自己来**：登录账号、充值、填 API Key 这几步交给用户，你告诉他在哪里填（可以建议他在终端里输入 `! <登录命令>` 自己跑）。不要让用户把密码或密钥发到对话里，你也不经手。

装好后回到第 3 步，读它的帮助，接着往下走。
