# OpenSpec 单 agent 工单 Apply

你一个人依次扮演执行者、审查者、验收员，不派任何子代理。工单、回执、PLAN.md 仍然落盘：工单是你每张单的依据和边界，回执是证据，也是上下文压缩或会话重启后续跑的唯一依据。

工作目录是仓库根下的 `_solo-self/`，只属于本技能，不与其他技能共用。格式文件都在本技能的 references/ 里：
- [工单图格式](references/plan.md)
- [工单格式](references/ticket.md)
- [回执格式](references/receipt.md)
- [通用规则清单](references/checklist.md)

## 少说话

- 过程中不向用户复述工单、计划、代码或命令输出，也不预告「接下来我要……」。命令输出只写进回执，而且只写结论和报错。
- 只在三种时候对用户说话：每张单提交后一行 `T<编号> 完成 <短 hash>（修复轮：<b,c 或 无>；存疑：<N>）`；需要用户决定时（见「停下来问」）；全部完成时。
- 开头只说一行「使用 change：<name>，续跑自 <T编号/阶段>」或「使用 change：<name>，新拆解」。

## 前提与准备

1. 选 change：用户点名就用；否则 `openspec list --json`，只有一个活动 change 就用它，多个就问。
2. `openspec instructions apply --change "<name>" --json`，读 `contextFiles` 和项目规矩（CLAUDE.md / RULES.md 等）。`all_done` → 提示归档并结束；`blocked` → 说明缺什么并停。
3. 建好 `_solo-self/{open,doing,done,blocked,dropped,_receipts}/`。
4. 工作区已有与本 change 无关的未提交改动时，提醒用户一次：提交只按路径提交本单文件，不会带上他们的改动。
5. 建议在新会话里开跑（提醒一次，不阻塞）：之前的讨论内容会在之后每个回合被重读。

## 续跑（每次被调用先做）

先看文件系统，不凭记忆。没有 `_solo-self/PLAN.md` → 进「一」。 否则看 `_solo-self/doing/` 里的单（一次只该有一张），读它的回执 `_solo-self/_receipts/T<编号>.md` 的**最后一节**：

| 状态 | 续跑位置 |
| --- | --- |
| 工单末尾已有 `提交：` | 「五」收尾里没做完的项 |
| 最后一节是「验收」且不通过 | 「四」开修复轮，来源是验收失败项 |
| 最后一节是「审查」或「复审」 | 「四」分诊 |
| 最后一节是「执行」 | 「三」审查 |
| 最后一节是「修复 <轮次>」 | 按「四」的复审条件：需复审进「三」复审，否则进「五」 |
| 没有回执 | 「二」执行：先 `git status --short` 看「只动」文件里有没有半成品，有就在其基础上接着做，不重写 |

`doing/` 为空 → 按 PLAN.md 取下一张前沿单。旧流程留下的 `T<编号>-exec.md` / `-review.md` 等回执也要读，按同样规则判断位置。

## 回执

每张单一个回执 `_solo-self/_receipts/T<编号>.md`，每个阶段结束时追加一节。格式见 [回执格式](references/receipt.md)，写回执前读它。

## 一、拆解：写 PLAN.md

读完 `proposal.md`、`design.md`、`specs/`、`tasks.md`，自己摸代码（要改的模块、入口、契约类型、测试命令和 fixture）。只读需要的片段，不整目录通读。

拆单规则：
- 一张单是一条能独立验证的纵切路径（类型 → 实现 → 调用方 → 测试）。需要先重构或补测试脚手架的，放最前面单独成单。
- 尺寸：通常改动 ≤5 个文件、验收 ≤4 条命令。已经很小的 openspec 任务保持一张单。
- 验收命令改动前会失败、改动后通过；只作用于本单的包和文件（`bun test <文件>`、`bunx tsc --noEmit -p <包>`、`npx eslint <文件>`）。纯类型/配置/文档单用 typecheck/lint/构建检查，并在「为什么这样验收」写明局限。
- 「必须保持」里「不改变既有行为」的条目，验收里要有测试锁住。
- 依赖只连真正卡住的边；编号顺序就是施工顺序。

模糊点自己拿主意：design 已定 → 照做；spec scenario 能推出 → 照推；代码惯例 → 跟随；都没有 → 选改动最小、最易回退的，记进 PLAN.md「拆解假设」。只有需要改变 spec 的范围、行为或对外接口时才停下来问。

写 PLAN.md 后自检：tasks.md 每个未勾选任务都被覆盖；每张单有确定的「只动」和能失败的验收；无环。

## 一·五、写工单

**一次只写下一张单**，写到 `_solo-self/doing/T<编号>-<短名>.md`，按工单格式填全；PLAN.md 该行改「进行中」。前面单的存疑常会改变后面的单，所以不提前写。「必须保持」写成能检查的条目并标出处；「适用通用规则」写清涉及清单的哪几类。

## 二、执行

1. 读工单、它列出的文件、`_solo-self/LESSONS.md`（存在时）、清单里适用的小节。
2. **先红**：先写测试，运行，确认失败，把关键失败行写进回执草稿（先记下，别等到最后）。
3. 实现，只动「只动」里的文件。按工单走不通（依赖缺失、spec 与代码矛盾、必须改边界外的文件）→ 回执状态写「中断」，进「六」。
4. **后绿**：跑工单全部验收命令。包级 typecheck 报错全部落在本单以外、且 `git status` 显示已有未提交改动的文件里 → 记「外部阻塞」，不算失败。
5. 追加回执「## 执行」。

## 三、审查（自审，但当作别人写的代码来审）

你刚写完的代码最容易带着同样的盲点被放过，所以审查必须照下面的步骤做，不能凭印象判断「没问题」：

1. 只看证据，不看记忆：`git diff -- <文件清单>`，新文件读全文。复审时只看来源条目涉及的改动。
2. 逐条对照工单「必须保持」和「为什么这样验收」：每条都要能在代码里指出实现位置、在测试里指出断言。指不出来就是一条发现。
3. 对照清单适用小节和 LESSONS.md 逐条过。
4. 查测试是否真的测到：断言落在实际行为（调用次数、写入内容、输出），不是只看返回值不抛错；边界上限内和超出一个单位两侧都有。
5. 查逻辑边界、误伤已有数据、安全（路径越界、密钥外泄、被绕过的审批）、稳定性（并发、超时、资源释放）。

每条发现标：严重程度（高/中/低）、归属（本单 / 超范围 / 改 spec）、类型（缺陷 / 测试）。不写风格建议，不凑数。追加回执「## 审查」（复审为「## 复审 <轮次>」）。

## 四、分诊与修复轮

- 无发现 → 「五」。
- 「超范围」→ 不修，记进后续单或存疑；「改 spec」→ 停下来问用户。
- **收敛**：从 c 轮起，类型「测试」的中/低发现不再开轮，结论记「存疑：测试 <编号>」后进「五」；只有「高」或「缺陷」才继续开轮。
- 其余 → 开修复轮（b、c、d、e），不写新工单，原工单仍是依据。可改文件 = 「只动」+ 条目点名的文件及其直接测试。逐条：
  1. 先红：写能复现的测试并运行，失败关键行记下；复现不了 → 判「不成立」并给证据，不改代码。
  2. 按类修：grep 同类写法，一并修，列出查过的位置。
  3. 后绿：同一测试通过，并重跑工单全部验收命令。
- 追加回执「## 修复 <轮次>」。修了「高」发现，或改了条目点名以外的非测试文件 → 回「三」复审；否则进「五」。
- 某类问题在别的单也出现过，或属于清单没覆盖的通用坑 → 验收收尾时往 `_solo-self/LESSONS.md` 追加一行 `- <类别>｜<规则>｜出处 T<编号>`。

**上限**：每张单最多 4 个修复轮。第 5 轮前停下来，用大白话告诉用户卡在哪、试过什么、建议（改方案 / 拆任务 / 改 spec / 放弃这一项）。

## 五、验收、提交、收尾

验收是一次独立重跑，不引用执行时的结果：

1. 工单「验收」里每条命令原样重跑；再跑项目规矩要求的全仓检查（本仓为 `bun run typecheck`、`bun run lint`）。报错全部落在本单以外、已有未提交改动的文件 → 外部阻塞，记下但不算失败。
2. 越界：`git status --short` + `git diff --stat`，本单产出（各节文件清单的并集）必须都在允许范围内。
3. 测试篡改：`git diff -- <测试文件>`，查有没有删测试、放宽断言、加 skip。
4. 每条修复轮来源条目都有结论；缺先红证据但有对应测试的，记存疑，不算失败。
5. 追加回执「## 验收」。不通过 → 回「四」开修复轮，来源是验收失败项。

通过后：
1. `git add <本单产出的每个文件>`，`git commit -m "<type>(<包>): T<编号> <摘要>" -- <同一批文件>`（提交信息风格跟随 `git log` 近几条）。只提交代码和测试产出，`_solo-self/` 下的文档不进提交（与 multi-apply 一致）。不许 `git add -A` / `.`。
2. 工单末尾追加：
   ```
   ## 记录
   - 提交：<hash>
   - 验收：通过（重跑 <N> 条命令）
   - 修正：<如「b（审查 1、2）」或「无」>
   - 存疑：<最多 3 条，没有写「无」>
   ```
3. 工单挪 `_solo-self/done/`；PLAN.md 该行改「完成」；`tasks.md` 勾掉对应任务；按需追加 LESSONS.md。
4. 对用户说一行完成消息，然后回「一·五」写下一张单。存疑影响后续单的范围、验收或依赖时，写下一张单时直接吸收，必要时改 PLAN.md。

## 六、中断

- 工单写错或太大 → 改写或拆分；原单挪 `dropped/` 并在末尾写原因，PLAN.md 同步。
- 缺外部条件（等密钥、等用户） → 挪 `blocked/`，末尾写清在等什么，继续下一张不依赖它的单。
- 暴露设计问题 → 小澄清直接更新 `design.md`/`specs/` 并在最终总结里说明；改变范围、行为或接口的，停下来问用户。

## 停下来问

只在这些时候问用户：改变 spec 的范围/行为/接口；修复轮到上限；安装软件或改模型/effort；删数据、删目录、强推、对外发消息等不可逆操作；多个活动 change 选不出。其余都自己拿主意并记进 PLAN.md 或回执。

## 全部完成时

用大白话、按用户能感知的功能说：现在能用了什么；用户可能注意到的变化；还剩的风险（存疑、自审可能漏掉的地方、`blocked/`/`dropped/` 里的单）；拆解时替用户做的判断；建议归档（openspec-archive-change）。

## 规矩

- 用用户的语言汇报。
- 密钥不写进代码、工单、回执和日志。
- 不 push；自检时起的后台进程收尾前关掉。
- 一次只做一张单，前一张提交并收尾后才开下一张。
