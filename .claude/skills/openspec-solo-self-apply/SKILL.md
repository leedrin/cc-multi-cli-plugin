# OpenSpec 单 agent 工单 Apply

你一个人依次扮演执行者、审查者、验收员，不派任何子代理。工单、回执、PLAN.md 仍然落盘：工单是你每张单的依据和边界，回执是证据，也是上下文压缩或会话重启后续跑的唯一依据。

工作目录是仓库根下的 `_solo-self/`，只属于本技能，不与其他技能共用。格式文件都在本技能的 references/ 里：
- [工单图格式](references/plan.md)
- [工单格式](references/ticket.md)
- [回执格式](references/receipt.md)
- [通用规则清单](references/checklist.md)
- 记录检查脚本 `scripts/records.mjs`（下称 **records**）：打印模板、检查工单/回执、巡检整个 `_solo-self/`。调用写法：`node <本技能目录>/scripts/records.mjs <子命令>`，本仓默认 `node .claude/skills/openspec-solo-self-apply/scripts/records.mjs <子命令>`；开跑时把实际路径写进 PLAN.md 命令表的「记录检查」一行。

## 不间断推进（最高优先级）

目标是**一次调用内**把 `tasks.md` 推进到全部完成。回合只允许在下面三种情况结束：① 全部完成；② 剩下的单全被 `blocked/` 挡住、无事可做；③ 命中「停下来问」。

- 每张单提交后的那一行消息只是**进度标记，不是收尾**：发出后紧接着在同一回合里继续下一步（读 PLAN.md、写下一张单、调用工具）。不以「接下来我将……」「要继续吗？」「先到这里」结束回合，也不请求确认。
- 不因为任务多、上下文长、已经做了很多而停下。上下文被压缩后，从文件系统按「续跑」接着做，不凭记忆。
- 遇到问题按这个顺序处理：自己解决 → 记进假设/存疑后继续 → 单挪 `blocked/` 后做下一张 → 才是停。
- 命令超出前台等待时限被转到后台：等它结束并读输出，不重复启动、不当成失败、不因此停下。
- 用户让你「停」时才停。

## 少说话（只管聊天，不管文件）

- 「少说话」**只约束对用户说的话**：过程中不向用户复述工单、计划、代码或命令输出，也不预告下一步。
- **它不适用于落盘的工单、回执、PLAN.md**。这些文件是后期追踪维护的唯一依据，每一张都必须写得和第一张一样完整（见下一节）。命令输出写进回执时只写结论和关键报错，但格式要求的每个字段、每一节都得有。
- 只在三种时候对用户说话：每张单提交后一行 `T<编号> 完成 <短 hash>（修复轮：<b,c 或 无>；存疑：<N>）`；命中「停下来问」；全部完成时。
- 开头只说一行「使用 change：<name>，续跑自 <T编号/阶段>」或「使用 change：<name>，新拆解」。

## 记录不许缩水（防飘移，最高优先级之一）

上下文被压缩或会话变长后，容易发生飘移：格式文件已不在上下文里，你开始模仿自己前几张越写越短的记录，最后工单只剩一句「已完成，见回执」、回执只剩几行。这会让后期无法追踪，所以下面这些**没有例外**：

1. **写之前取模板，不凭记忆、不模仿上一张**：写工单前跑 `records skeleton ticket`，写回执前跑 `records skeleton receipt`，把打印出来的模板整份填全。第 1 张和第 50 张用同一份模板。
2. **写完立刻检查，不过不往下走**：
   - 工单写完 → `records ticket <工单文件>`
   - 回执每追加一节 → `records receipt <回执文件>`
   - 提交前 → `records receipt <回执文件> --complete`
   - 提交后写完工单「## 记录」→ `records ticket <工单文件> --done`
   - 检查输出 `ERROR` 就当场补全，直到 `OK`。不得以「已提交 / 已通过 / 内容在 git 里」为由跳过。
3. **自审那一节必须有**：写不出具体发现时，写「无发现（查了什么：…，≥8 字）」，不能只写「无发现」或整节省略。
4. **已完成的工单不改写成指针**：不得把工单内容替换成「已完成，见回执」「done <hash>」之类的一行话；`done/` 里的工单必须保留完整正文并追加「## 记录」。
5. **合并工单不留占位行**：两张单合成一张时，不要给没有任务的编号留一行「并入 Txx」的 PLAN.md 行，也不要缺文件；要么不占这个编号，要么把原单挪 `dropped/` 并写明并入哪张。PLAN.md 每行的「openspec 任务」必须有具体任务号。
6. **巡检**：每次续跑开头、每个阶段门禁后、以及全部完成前，跑 `records audit`。有 `ERROR` 先回头补齐（历史记录能从 `git show`、回执和 tasks.md 还原的就还原，还原不了的在记录里写明「当时未记录」，不编造），`WARN`（篇幅骤降）要打开看一眼是否缩水。
7. 过程日志、临时脚本（`*.log`、`*.ps1`、`*.txt` 等）一律放 `_solo-self/_logs/`，不散落在 `_solo-self/` 根目录；`_solo-self/` 根下只留 PLAN.md、LESSONS.md 和各状态目录。
8. **没有 Node 时的兜底**：`records` 跑不了（命令不存在且装不了）→ 记进 PLAN.md「拆解假设」，改为人工逐项核对 ticket.md / receipt.md 末尾的「自检清单」，每张单在回执末尾写一行「人工自检：通过」。不能因此省略任何字段。

## 运行环境

- **权限**：本流程要无人值守地执行 git add/commit/status/diff/log/show、项目的测试/lint/类型检查、`openspec`、读写仓库文件。会话须处于免审批模式（如 Claude Code 的 `bypassPermissions`，或 `.claude/settings.local.json` 的 allow 列表覆盖这些命令；别放开 `Agent`）。命令被审批挡住时，改用等价的免审批命令，别停下来等。
- **Shell（Windows PowerShell 5.1 也要能跑）**：命令用 `;` 串接，别用 `&&`；要看失败就检查 `$LASTEXITCODE`。不用 bash 花括号展开（`a/{b,c}`）、`mkdir -p`、`cat`/`head`/`grep`；读文件用 Read 工具。多行提交信息用多个 `-m`，字符串里不写 `\n`。
- **命令表**：跑任何验收前，先从 `package.json` 的 scripts、`CLAUDE.md`/`AGENTS.md` 及其引用里确定这几条命令并写进 PLAN.md 的「命令表」，之后一律照表：单文件测试、按文件 lint、类型检查、全仓门禁（含 lint、死代码检查、测试的那条），以及项目特有的检查（如 hook 层测试），外加一行「记录检查」（records 的实际调用路径）。不套用别的项目的命令。
- 依赖缺失（`node_modules` 不存在等）→ 装项目声明的依赖（`npm ci` 等），不必问。
- 命令依赖外部条件（缺登录、缺生成物、缺可执行文件、要联网、付费）→ 只尝试一次准备；仍不行就记「外部阻塞」，改用可用的替代验收并在回执标注，此后同类命令不再重试。

## 前提与准备

1. 选 change：用户点名就用；否则 `openspec list --json`，只有一个活动 change 就用它，多个就问。
2. `openspec instructions apply --change "<name>" --json`，读 `contextFiles` 和项目规矩。`state` 为 `all_done` → 提示归档并结束；`blocked` → 说明缺哪个 artifact 并停。
3. 确定命令表（见「运行环境」），确定分支：当前不在 `main`/`master` 就用当前分支，不新建、不切换；在主干上就建 `feat/<change 名>`。tasks.md 里的分支任务与当前分支不一致时，以当前分支为准，记进 PLAN.md「拆解假设」。
4. 建 `_solo-self/` 下的 `open`、`doing`、`done`、`blocked`、`dropped`、`_receipts`、`_logs` 七个目录（逐个 `New-Item -ItemType Directory -Force`，不要用花括号）。再把 `/_solo-self/` 追加进 `.git/info/exclude`（已有则跳过），让它不出现在 `git status` 里。
5. 工作区已有与本 change 无关的未提交改动时，提醒用户一次：提交只按路径提交本单文件，不会带上他们的改动。change 目录（`openspec/changes/`）没被 git 跟踪时，勾选 tasks.md 不进提交，也不算越界。
6. 建议在新会话里开跑（提醒一次，不阻塞）。

## 续跑（每次被调用先做）

先看文件系统，不凭记忆。没有 `_solo-self/PLAN.md` → 进「一」。否则先重读本文件的「记录不许缩水」，跑一次 `records audit`（有 `ERROR` 先补齐再往下），再看 `_solo-self/doing/` 里的单（一次只该有一张），读它的回执 `_solo-self/_receipts/T<编号>.md` 的**最后一节**：

| 状态 | 续跑位置 |
| --- | --- |
| 工单末尾已有 `提交：` | 「五」收尾里没做完的项（挪 done、改 PLAN.md、勾 tasks.md） |
| 最后一节是「验收」且通过、无 `提交：` | 先 `git log -5 --oneline` 和 `git status --short -- <文件清单>` 核对：已提交（清单里的文件已无改动、log 里有对应提交）→ 补「记录」并收尾；未提交 → 做提交 |
| 最后一节是「验收」且不通过 | 「四」开修复轮，来源是验收失败项 |
| 最后一节是「审查」或「复审」 | 「四」分诊 |
| 最后一节是「执行」 | 「三」审查 |
| 最后一节是「修复 <轮次>」 | 按「四」的复审条件：需复审进「三」复审，否则进「五」 |
| 没有回执 | 「二」执行：先 `git status --short` 看「只动」文件里有没有半成品，有就在其基础上接着做，不重写 |

`doing/` 为空 → 按 PLAN.md 取下一张前沿单（状态「待办」且被谁阻塞的单都已「完成」）。旧流程留下的 `T<编号>-exec.md` / `-review.md` 等回执也要读，按同样规则判断位置。

## 回执

每张单一个回执 `_solo-self/_receipts/T<编号>.md`，每个阶段结束时追加一节。格式见 [回执格式](references/receipt.md)；**每次**写回执前先跑 `records skeleton receipt` 取模板，追加后跑 `records receipt <文件>`（见「记录不许缩水」）。回执用 UTF-8 无 BOM、不要整份重写已有的节。

## 任务类型与并单

tasks.md 里的任务不都是「写代码」。拆解时先给每条任务定类型，处理方式如下：

| 类型 | 处理 |
| --- | --- |
| 约定类（如「提交约定」「记录基线」） | 不单独成单，随首张相关单一并勾选 |
| 门禁类（只是「运行全仓检查 / hook 测试」） | 不单独成单，并入同阶段最后一张单的验收，通过后一并勾选；失败了按「五」建修复单 |
| 表征 / 回归锁定类（给现有行为加测试，改动前就会通过） | 无先红。验收改为**变异验证**：临时改动被测行为（或把断言的预期值改错）确认测试确实变红，再用编辑工具把改动原样撤回（**不用** `git checkout` / `git stash` / `git restore`：它们会连本单尚未提交的成果一起抹掉），把这一步写进回执 |
| 文档 / 清单 / 记录模板类 | 轻量路径：执行 → 自审（逐条对照 spec 条目）→ 验收（lint/格式检查 + 引用的命令和路径确实存在）→ 提交。无先红 |
| 需要外部条件才能真跑的类（手工 GUI 验证、多版本对比、付费 live 探测、联网 rebase 演练） | 先做能离线完成的部分（清单、夹具、脚本、记录模板），实际执行按「运行环境」只试一次；跑不了 → 单挪 `blocked/`，tasks.md 里**不勾选**，任务行末追加 `⏸ 待外部条件：<原因>`，最终报告里列出。不要为了「全部完成」而勾选没做的事 |
| 代码类 | 正常走「二」到「五」 |

## 一、拆解：写 PLAN.md

读完 `proposal.md`、`design.md`、`specs/`、`tasks.md`，自己摸代码（要改的模块、入口、契约类型、测试命令和 fixture）。只读需要的片段，不整目录通读。

拆单规则：
- 一张单是一条能独立验证的纵切路径（类型 → 实现 → 调用方 → 测试）。需要先重构或补测试脚手架的，放最前面单独成单。
- 尺寸：以 tasks.md 的 `## N` 任务组为主线，一张单可覆盖相邻、验收相同的几条小任务（≤6 条）；通常改动 ≤5 个文件、验收 ≤4 条命令。
- 验收命令改动前会失败、改动后通过（表征/文档类见上表）；用命令表里只作用于本单文件的形式（单文件测试、按文件 lint），加一次类型检查。纯类型/配置/文档单用 typecheck/lint 检查，并在「为什么这样验收」写明局限。
- 「必须保持」里「不改变既有行为」的条目，验收里要有测试锁住。
- 全仓门禁里若有「死代码/未使用导出」检查：新模块的导出必须在同一张单里被测试或调用方引用，否则调整拆单顺序或把桩和首个使用者放进同一张单。
- 新模块的单先建导出桩（抛 `not implemented`），让「先红」红在断言上，而不是红在「找不到模块」。
- 依赖只连真正卡住的边；编号顺序就是施工顺序。

模糊点自己拿主意：design 已定 → 照做；spec scenario 能推出 → 照推；代码惯例 → 跟随；都没有 → 选改动最小、最易回退的，记进 PLAN.md「拆解假设」。

写 PLAN.md 后自检：tasks.md 每个未勾选任务都被某张单覆盖或明确归入「随单勾选/外部条件」；每张单有确定的「只动」和能失败的验收（或变异验证）；无环。

## 一·五、写工单

**一次只写下一张单**，先跑 `records skeleton ticket` 取模板（不要照上一张单改），整份填全后写到 `_solo-self/doing/T<编号>-<短名>.md`，立刻跑 `records ticket <文件>` 到 `OK`；PLAN.md 该行改「进行中」。前面单的存疑常会改变后面的单，所以不提前写。「必须保持」写成能检查的条目并标出处；「适用通用规则」写清涉及清单的哪几类。

## 二、执行

1. 读工单、它列出的文件、`_solo-self/LESSONS.md`（存在时）、清单里适用的小节。
2. **先红**（表征/文档类按「任务类型」）：先写测试，运行，确认失败，把关键失败行写进回执草稿（先记下，别等到最后）。
3. 实现，只动「只动」里的文件。按工单走不通（依赖缺失、spec 与代码矛盾、必须改边界外的文件）→ 回执状态写「中断」，进「六」。
4. **后绿**：跑工单全部验收命令。类型检查/lint 报错全部落在本单以外、且 `git status` 显示已有未提交改动的文件里 → 记「外部阻塞」，不算失败。
5. 追加回执「## 执行」，跑 `records receipt <回执文件>`，`ERROR` 清零才进「三」。

## 三、审查（自审，但当作别人写的代码来审）

你刚写完的代码最容易带着同样的盲点被放过，所以审查必须照下面的步骤做，不能凭印象判断「没问题」：

1. 只看证据，不看记忆：`git diff -- <文件清单>`，新文件读全文。复审时只看来源条目涉及的改动。
2. 逐条对照工单「必须保持」和「为什么这样验收」：每条都要能在代码里指出实现位置、在测试里指出断言。指不出来就是一条发现。
3. 对照清单适用小节和 LESSONS.md 逐条过。
4. 查测试是否真的测到：断言落在实际行为（调用次数、写入内容、输出），不是只看返回值不抛错；边界上限内和超出一个单位两侧都有。
5. 查逻辑边界、误伤已有数据、安全（路径越界、密钥外泄、被绕过的审批）、稳定性（并发、超时、资源释放）。

每条发现标：严重程度（高/中/低）、归属（本单 / 超范围 / 改 spec）、类型（缺陷 / 测试）。不写风格建议，不凑数。追加回执「## 审查」（复审为「## 复审 <轮次>」）并跑 `records receipt`；没有发现也必须写「无发现（查了什么：…）」，这一节不能省。

## 四、分诊与修复轮

- 无发现 → 「五」。
- 「超范围」→ 不修，记进后续单或存疑；「改 spec」→ 不停下来问：采用改动最小、最易回退的解读，在 `design.md` 末尾「实施期决策补充」记一条（写清依据），继续；只有与 proposal/design 的 Non-Goals 或用户的硬约束直接冲突才命中「停下来问」。
- **收敛**：从 c 轮起，类型「测试」的中/低发现不再开轮，结论记「存疑：测试 <编号>」后进「五」；只有「高」或「缺陷」才继续开轮。
- 其余 → 开修复轮（b、c、d、e），不写新工单，原工单仍是依据。可改文件 = 「只动」+ 条目点名的文件及其直接测试。逐条：
  1. **先找根因，再改**：从症状出发，沿逻辑链和数据链梳理，并**对照原版**（本仓的基线 / `upstream` 上的同名文件 / spec 与 design 的原文）看哪里和原版不一致；没找到根因前不加兜底、补偿或吞错。然后写能复现的测试并运行，失败关键行记下；复现不了 → 判「不成立」并给证据，不改代码。
  2. 按类修：grep 同类写法，一并修，列出查过的位置。
  3. 后绿：同一测试通过，并重跑工单全部验收命令。
- 追加回执「## 修复 <轮次>」（跑 `records receipt`）。修了「高」发现，或改了条目点名以外的非测试文件 → 回「三」复审；否则进「五」。
- 某类问题在别的单也出现过，或属于清单没覆盖的通用坑 → 验收收尾时往 `_solo-self/LESSONS.md` 追加一行 `- <类别>｜<规则>｜出处 T<编号>`。

**上限**：每张单最多 4 个修复轮。第 4 轮仍不通过时**不停下来问**：在回执写「## 卡住」（症状、根因分析、试过什么、建议改方案/拆任务/改 spec/放弃），单挪 `blocked/`，PLAN.md 改「阻塞」，继续下一张不依赖它的单。只有剩下的单全都依赖它时才结束回合并报告。

## 五、验收、提交、收尾

验收是一次独立重跑，不引用执行时的结果：

1. 工单「验收」里每条命令原样重跑（表征类另做变异验证）；再跑命令表里的类型检查和 lint。报错全部落在本单以外、已有未提交改动的文件 → 外部阻塞，记下但不算失败。
2. 越界：`git status --short` + `git diff --stat`，本单产出（各节文件清单的并集）必须都在允许范围内（`_solo-self/` 已被排除；未跟踪的 change 目录不算）。
3. 测试篡改：`git diff -- <测试文件>`，查有没有删测试、放宽断言、加 skip。
4. 每条修复轮来源条目都有结论；缺先红证据但有对应测试的，记存疑，不算失败。
5. 追加回执「## 验收」。不通过 → 回「四」开修复轮，来源是验收失败项。

通过后：
0. 提交前门：`records receipt <回执文件> --complete` 必须 `OK`（要求有审查、且最后一节是通过的验收）。不过就补，不提交。
1. `git add <本单产出的每个文件>`，`git commit -m "<摘要>" -- <同一批文件>`。提交信息风格：change 的 design/proposal 里给了提交序列（如小提交清单）就用那里的格式和措辞；没给就跟随 `git log` 近几条。不在提交信息里写工单编号。只提交代码、测试和被要求的文档产出，`_solo-self/` 下的文件不进提交。不许 `git add -A` / `.`。本技能的提交规则优先于仓库里通用的 commit 类技能，不必再另行调用。绝不在 `main`/`master` 上提交。
2. 提交后核对：`git show --stat --name-only HEAD` 的文件集合等于本单文件清单；不等就是漏加或多加，先修正（`git commit --amend` 仅限刚做的这一次提交）。
3. 工单末尾追加：
   ```
   ## 记录
   - 提交：<hash>
   - 验收：通过（重跑 <N> 条命令）
   - 修正：<如「b（审查 1、2）」或「无」>
   - 存疑：<最多 3 条，没有写「无」>
   ```
   写完跑 `records ticket <工单文件> --done`（会核对提交 hash 真实存在、工单正文未被缩水），`OK` 才继续。
4. 工单挪 `_solo-self/done/`（整份正文保留，不改写成指针）；PLAN.md 该行改「完成」；`tasks.md` 里勾掉本单覆盖的每条任务（`- [ ]` → `- [x]`，含随单勾选的约定类和并入的门禁类）；按需追加 LESSONS.md。
5. **阶段门禁**：一个 `## N` 任务组的最后一张单收尾后，跑 `records audit`（`ERROR` 清零）和命令表的全仓门禁。通过则继续；失败且问题属于本 change → 新建一张修复单（编号顺延，走完整流程），不改已提交单的记录；失败全落在本 change 之外的未提交文件 → 记外部阻塞，继续。
6. 对用户说一行完成消息，**然后立刻回「一·五」写下一张单**（见「不间断推进」）。存疑影响后续单的范围、验收或依赖时，写下一张单时直接吸收，必要时改 PLAN.md。

## 六、中断

- 工单写错或太大 → 改写或拆分；原单挪 `dropped/` 并在末尾写原因（`原因：…`，并入别的单就写明并入哪张），PLAN.md 同步（PLAN.md 里要有这一行，状态「放弃」）。
- 缺外部条件（等密钥、等登录、等用户） → 挪 `blocked/`，末尾写清在等什么（`原因：…`），PLAN.md 同步（状态「阻塞」），继续下一张不依赖它的单。`blocked/` 里的单也要有完整正文。
- 暴露设计问题 → 小澄清直接更新 `design.md`/`specs/` 并在最终总结里说明；改变范围、行为或接口的按「四」处理，不停下来问。

## 停下来问

只在这些时候问用户：删数据、删目录、强推、`push`、对外发消息等不可逆或对外可见的操作；安装全局软件或改模型/effort；多个活动 change 选不出；剩下的单全被外部条件挡住且没有可做的事；与 proposal/design 的 Non-Goals 或用户硬约束直接冲突。其余都自己拿主意并记进 PLAN.md 或回执。

## 全部完成时

先跑 `records audit`，`ERROR` 必须清零（补不了的按「记录不许缩水」第 6 条注明）；`audit` 不通过不得宣布完成。再判定：`openspec instructions apply --change "<name>" --json` 的 `progress.remaining` 为 0，或剩余的任务全带 `⏸ 待外部条件` 且对应单在 `blocked/`。**以这个命令的结果为准，不以 PLAN.md 为准**；有未勾选且不属于上述两类的任务 → 说明漏了单，回「一」补拆，不结束。

然后用大白话、按用户能感知的功能说：现在能用了什么；用户可能注意到的变化；还剩的风险（存疑、自审可能漏掉的地方、`blocked/`/`dropped/` 里的单及原因、外部阻塞的检查）；拆解时替用户做的判断；建议归档（openspec-archive-change）。

## 规矩

- 用用户的语言汇报。
- 不派子代理，不请子代理审查。
- 工单和回执永远写满：不因「少说话」「上下文长」「已经提交」而缩写，不模仿前面变短的记录，每次从 records 的模板起笔。
- 密钥不写进代码、工单、回执和日志。
- 不 push；自检时起的后台进程收尾前关掉。
- 一次只做一张单，前一张提交并收尾后才开下一张。
