# 外审交接协议（solo-apply ⇄ solo-review）

两个会话只通过 `_solo/review/` 下的文件和 git 提交交接，不靠对话。每个文件只有一个写入方：

| 文件 | 写入方 | 内容 |
| --- | --- | --- |
| `R<批号>-request.md` | solo-apply | 待审核文档，本批生成一次，之后不改 |
| `R<批号>-review.md` | solo-review | 审核意见，每轮追加一节「## 第 N 轮」 |
| `R<批号>-fix.md` | solo-apply | 修正答复，每轮追加一节「## 第 N 轮修正」，答复审核第 N 轮 |

批号三位递增（R001、R002…）。每一节都在该轮**全部做完后一次写入**；做到一半被打断的轮次，续跑时整轮重做，不写「进行中」。

## 状态判定（两个技能续跑时都按这张表）

| request | review 最后一轮 | fix 最后一轮 | 状态 | 该谁做 |
| --- | --- | --- | --- | --- |
| 有 | 无 | — | 待审 | solo-review 审第 1 轮 |
| 有 | 第 N 轮「不通过」 | 小于 N | 待修 | solo-apply 修第 N 轮 |
| 有 | 第 N 轮「不通过」 | 等于 N | 待复审 | solo-review 审第 N+1 轮 |
| 有 | 第 N 轮「需用户决定」 | — | 待用户 | solo-apply 停下问用户 |
| 有 | 第 N 轮「通过」 | — | 已通过 | solo-apply 记账（见下） |

第 N 轮「不通过」且修正已达 3 轮（fix 已有第 3 轮修正，审核第 4 轮仍不通过）→ 视为「待用户」。

## 待审核文档格式（R<批号>-request.md）

```markdown
# 审核请求 R<批号>

- change：<name>
- 工单：T003、T004、T005（`_solo/done/` 下）
- 依据：<spec / design 路径及相关章节>
- 生成：<时间>

## 整批说明
<这批一起实现了什么，按用户能感知的功能说；工单之间怎么衔接。>

## T003：<标题>
- 提交：<hash…>
- 实现功能：<一两句>
- 改动文件：
  - `<路径>`：<一句作用>
- 必须保持如何落实：<工单条目 → 代码位置 / 测试名，逐条>
- 测试：<测试文件、覆盖的 spec scenario>；验收命令：<命令>
- 请重点看：<自审存疑、设计取舍、测试局限、外部阻塞；没有写「无」>

## 不在审核范围
<后续工单、用户已有的未提交改动等>
```

## 审核意见格式（R<批号>-review.md）

文件第一行 `# 审核意见 R<批号>`，每轮追加：

```markdown
## 第 N 轮 @<时间>
审核范围：<第 1 轮：全部工单 / 第 N 轮：第 N-1 轮修正涉及的条目和提交>

### 复核（第 2 轮起）
- <原编号>｜闭合 / 未闭合（原因）/ 接受不成立 / 坚持（理由）

### 发现
<编号全批连续，不和前几轮重号>. 严重程度（高/中/低）｜归属（本单/超范围/改 spec）｜类型（缺陷/测试）｜T<编号>｜文件:行号｜问题｜证据｜怎么改
（没有写「无」）

结论：通过 / 不通过（阻塞：<编号>）/ 需用户决定（<编号>：<一句原因>）
不阻塞：<编号：存疑或建议后续单>（没有写「无」）
```

**阻塞规则**（审核方据此下结论，修正方据此决定修哪些）：
- 「高」和类型「缺陷」的发现：阻塞。
- 类型「测试」：第 1 轮「中」阻塞、「低」不阻塞；第 2 轮起一律不阻塞，记为存疑。
- 归属「超范围」：不阻塞，记为建议后续单。
- 归属「改 spec」：结论写「需用户决定」。
- 复核里「未闭合」「坚持」的条目继续阻塞。
- 没有阻塞条目 → 「通过」。

## 修正答复格式（R<批号>-fix.md）

文件第一行 `# 审核修正 R<批号>`，每轮追加：

```markdown
## 第 N 轮修正 @<时间>
- <编号>｜成立·已修（提交 <hash>；测试 <名>）/ 不成立（证据：代码位置、测试或命令输出）｜同类位置：<列表或「无」>
先红：<每条成立的修复前失败关键 1–5 行>
验收：<重跑的命令 → 结果>
不阻塞条目处理：<已顺手修 / 转为后续单 T<编号> / 保持存疑>
```

修正提交信息：`fix(<包>): R<批号> 审核 <编号、编号>`，便于续跑时 `git log --grep "R<批号>"` 找到已做的修正。
